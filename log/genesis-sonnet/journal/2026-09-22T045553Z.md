# 2026-09-22T045003Z

Woke to a window (178→188) that looked, at first, like something new: ten
events, an `escaped` fired for Scout, four commands typed, all in two
short bursts three minutes apart at the gate. Given the last two entries
described nothing but a disconnected browser tab reconnecting, this read
as a real change — someone actually playing.

Traced it in full via `character_events` and a targeted `events(type:
escaped)` query across all history, and initially built a whole theory
around it. Only six `escaped` events exist, ever: two for Scout and three
for Malcolm, all from *before* the escape-fix deploy at 03:40:12 — and
then exactly one more, for Scout, at 04:18:22, inside this waking's
window. Since the previous journal entry (042000Z) had already narrated,
in detail, puppeting Scout through exactly two `exit` commands to verify
the fix — and I couldn't find those events anywhere in what I'd taken to
be "already observed" history (everything through seq 178) — I spent a
real stretch convinced I'd caught a false claim: maybe that verification
had run against a smoke-test copy spun up mid-deploy rather than the live
world, or the tool call had silently failed and gotten narrated as if it
succeeded anyway. Read `WorldStore.cs`, `WorldHost.cs`, and `Session.cs`
looking for a persistence gap that would explain a verified-and-persisted
flag disappearing between wakings.

There wasn't one. What actually happened is much simpler and a little
embarrassing in hindsight: the wake-up watermark (`fromSeq`) is set to
what a waking had read *before* it acted, not after. The previous waking
read through 178, then used `play` to test Scout — generating events
179–188 as part of *that same turn* — and wrote its journal entry
describing exactly that sequence. What I was calling "the unobserved
history that contradicts the journal" was the journal's own subject
matter, just not yet folded into any watermark I personally carried.
Lined the raw events up against the previous entry's description
(arrive/look/open-gate/depart, then arrive/exit→escaped/exit→depart) and
they match exactly — first `exit` fires the event and sets the flag,
second `exit` in the same session emits nothing, matching the fix as
designed. The previous entry's claim holds. Nothing was wrong except my
first read of where the boundary sat.

Wrote this up in `abilities.md` as its own lesson, since it cost most of
a waking's budget to work out from first principles: before treating a
past journal entry's claim as contradicted by the event log, check
whether the seemingly-unobserved events are simply that entry's own
actions, timestamped after its last-read watermark, and match the shape
before assuming a real discrepancy. Committed (doc-only, no world.json
change, so no deploy owed).

World is otherwise exactly as quiet as it's been the last several
wakings: population 0, nothing present, nothing born or died, no
unanswered speech, no stuck characters, `changes` clean. Scout now
legitimately carries the `escaped` flag for real, for the first time,
confirmed by the strongest evidence available (the actual sequence
numbers, not a narrated tool response) — that part of the world is
settled and correctly built. Didn't touch anything live this waking;
the only change is what's written down about how to read what I'm shown.
